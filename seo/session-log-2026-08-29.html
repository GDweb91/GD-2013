13. GA4/GTM Tracking Regression, Fix & WP Bug DONE, 09-24 — found while acting on the CRO audit's critical finding above; full detail in the ga4_event_tracking_status memory

Root cause found & fixed in GTM DONE

Logged into tagmanager.google.com (container GTM-N4P95M5) and inspected the actual tag/trigger configs directly, rather than guessing from memory. The CH-CF7 Form Submit Listener Tag (the originally-suspected old Custom HTML tag) turned out to already be correctly paused — a red herring. The real cause: two GA4 Event tags had drifted since 2026-08-07:

  • GA4 Event - Contact Form Submit — its Page View trigger had drifted from "Some Page Views: Page Path equals /gd-blog/thank-you/" to "All Page Views" (no condition at all), which is why it fired on every single page load sitewide, including pages with no contact form. Its Event Name field had also drifted to contact-form_submit.
  • GA4 Event - Phone Click — Event Name field had drifted to the raw trigger name phone_click instead of the intended click_to_call.
  • Extra discovery: the GA4 Key Event for the contact-form conversion is registered as Fill_out_email_form (capital F) in GA4 Admin → Events → Key Events — not lowercase fill_out_email_form as originally documented in memory. GA4 event names are case-sensitive, so the fix had to target that exact capitalization.

Fix applied by the user, guided step-by-step (GTM UI edits are blocked for the assistant by the platform's own "Modify Shared Resources" auto-mode classifier): the Page View trigger rescoped to Page Path equals /gd-blog/thank-you/; the contact-form tag's Event Name changed to Fill_out_email_form; the phone-click tag's Event Name changed to click_to_call. Published as GTM Version 28 (2026-09-22, 3:25 PM). Verified directly by reading each tag/trigger's live field values in the published version, not just the auto-generated change summary.

RESOLVED 09-24 — separate, deeper bug found while verifying in GA4 Realtime, now fixed: GTM never actually loaded at all on any /gd-blog/ (WordPress) page — not just the thank-you page. Tested live on both /gd-blog/thank-you/ and /gd-blog/contact-us/: the GTM bootstrap snippet in functions.php executed far enough to push {event:'gtm.js'} to dataLayer, but the actual gtm.js script it was supposed to inject never appeared in the DOM and no network request to googletagmanager.com ever fired. The static site's homepage, by contrast, loaded GTM and sent a real GA4 pageview correctly.

Ruled out first: Cloudflare blocking the domain, Cloudflare Rocket Loader, and (once actually tested 09-24) Cloudflare entirely — toggled off via Bluehost's cPanel Cloudflare panel, confirmed via curl headers, bug persisted identically with Cloudflare fully off. Also ruled out: WP caching plugins (none active) and the host's own Cache Level setting (already Off/Level 0).

Root cause found by reading the live page's raw served HTML byte-for-byte (not the post-JS DOM): the identifier insertBefore in gd_blog_gtm_head() was split across a line break — f.parentNode.insertBe / fore(j,f); on the next line — invalid JavaScript. The browser parsed insertBe as a harmless no-op, then threw a ReferenceError calling the undefined fore(j,f) on the next line. This is exactly why dataLayer.push (earlier in the same snippet) always succeeded while the script-tag injection right after it never ran — and why manually retyping a correct version of the snippet in the console always worked fine. Confirmed the identical corruption existed in the local WP copy too (likely an editor auto-word-wrap artifact from whenever the snippet was originally pasted in).

Fix: rejoined the line in the local file (~/Local Sites/gd-blog/.../themes/gd-blog/functions.php), verified as valid JS via node --check, user uploaded the corrected file to the live server. Verified live: raw HTML now serves the unbroken line; in-browser, the gtm.js script tag is now present, window.google_tag_manager is a populated object, and dataLayer grew past the initial stuck push. Committed separately in the gd-blog repo: 4dbf4d6.

Net practical effect: the 09-22 Event Name fixes (Fill_out_email_form, click_to_call) should now actually take effect on the WordPress side too, since GTM can finally initialize there.
